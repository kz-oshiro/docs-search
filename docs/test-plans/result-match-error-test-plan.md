# 結果ラベル・エラー表示の確認方針

現行の実行入口は[開発手順](../development.md)、機能基準は[Rust要求仕様](../specifications/rust-requirements.md)、実施結果は[公開・検証記録](../releases/README.md)を参照する。試験設計は同じ文書を更新し、改訂履歴をGitで管理する。

> 2026-10-04方針更新: 試験はバックエンド試験・フロントエンド試験・アプリケーション結合試験の3区分とする。バックエンド試験・[フロントエンド試験](playwright-ui-test-plan.md)でカバーできないもののみ[アプリケーション結合試験](playwright-exe-test-plan.md)へ回す。要求引数・表示・構造/配色はフロントエンド試験で担当し、G01/G02を実EXEへ重複させない。追加ランナー・拡張は未実装。Rust製OS操作補助は導入せず、ネイティブダイアログ・実クリップボード・既定アプリ・排他ロック・OS表示は保証対象外とする。M1〜M5の必須手動票は廃止。以下のGUI手順・未実施・許可の記述は旧方針の参考記録であり、現在の必須手動作業として依頼しない。

この方針は `matchCategory` と検索結果・エラー欄の表示変更に適用する。リポジトリの `AGENTS.md` に従い、GUI テストは依頼または事前確認がある場合だけ実施する。

## 自動確認と配布ビルド

自動テストのみの依頼では、リポジトリ直下で下表の入口を実行する。Windows配布ビルドまで依頼された場合は、同じ自動一式を含む `cargo xtask ci` に代える。

| 確認項目 | 手順 | 期待結果 |
| --- | --- | --- |
| 既存検索の回帰 | `cargo xtask test` を実行する。 | 共通バックエンドケース、Rustテスト、JS構文確認、UI資材staging、ヘッドレスUI試験が成功する。結果件数・順位・強調範囲が変わらない。 |
| 一致区分 | 共通ケース `basic-search-excludes-fuzzy-variants`、`fuzzy-identifier-variants`、`fuzzy-width-and-spacing`、`fuzzy-typo-candidate` の結果を照合する。 | 通常検索の結果は `standard`。あいまい検索オンでも通常検索で見つかる原文・大小文字差・部分一致は `standard`。幅差、識別子差、タイプミスなど通常検索で見つからない結果は `fuzzy`。`matchType` と `score` の既存の期待値は維持する。 |

## GUI

保存用データは [共通テストデータの手順](../../tests/README.md)で新しい出力先に生成する。アプリをビルドした後、生成先の `search/fuzzy` または `search/errors` を検索フォルダーとして指定する。

| 確認項目 | 手順 | 期待結果 |
| --- | --- | --- |
| 一致ラベル | `search/fuzzy`、拡張子 `.md`、検索語 `customerId` で、あいまい検索オフとオンを順に実行する。 | オフでは1・2行目に緑系の「一致検索」が出る。オンでも1・2行目は「一致検索」、3～6行目は黄系の「あいまい検索」。各箇所の一致理由、場所、抜粋、コピー操作が残る。 |
| 部分一致とタイプミス | 同じフォルダーで `customer` をあいまい検索オンで実行する。 | `customerId` を含む行は、理由が「識別子一致」でも通常検索で見つかるため「一致検索」。`custmer` は「あいまい検索」「タイプミス候補」。 |
| 絞り込みと再検索 | 一致とあいまいの混在結果を表示した状態でファイル名・拡張子の絞り込みと解除を行い、別の検索を開始する。 | 表示中の各一致区分が変わらず、結果件数と表示件数が整合する。再検索後は新しい結果だけが表示される。 |
| 個別エラーのみ | `search/errors`、検索語 `beacon`、拡張子 `.docx`・`.pptx`・`.txt` で検索する。 | 進捗下に赤系の「検索中のエラー」と件数が出る。展開すると各行で「読み取りエラー」、対象パス、理由が読める。結果が0件でもエラー欄は残る。 |
| 結果とエラーの併存 | 同じフォルダーと拡張子で `broken` を検索する。 | 壊れたファイルのファイル名一致が結果に残り、そのファイルカードに赤系の「エラーあり」が出る。進捗下のエラー欄にも同じパスと理由が出る。完了状態は黄系の「完了（一部エラーあり）」で、全体失敗の赤系と区別できる。 |
| 列挙エラー | 読み取り権限のないサブフォルダーを検索フォルダー内に用意して検索する。 | エラー欄に「列挙エラー」、取得可能なパスと理由が出る。検索できる他のファイルの結果は保持される。 |

静的確認では `git diff --check`、`SearchHit.matchCategory` と画面ラベルの対応、文書と共通ケースの整合を確認する。静的確認だけではビルド成功や GUI 表示を保証しない。
