# アプリケーション結合試験の設計（Playwright＋実Tauri）

2026-10-04 方針更新。状態: **設計文書のみ整備済み。実EXE用ランナー・追加ケース・Cargo入口の変更は未実装で、追加試験は未実施**。公開版の検証記録は [GitHub Releases](https://github.com/kz-oshiro/docs-search/releases)を参照する。

入口とCI制御はRustの `cargo xtask` に維持し、アプリケーション結合試験をPlaywrightで自動化する。Rust製OS操作補助、UI Automation、FlaUI、Python、.NET、WebdriverIOは追加しない。OS連携の保証対象外項目は文書に残し、人による確認を通常の完了条件にしない。この方針は従来のM1〜M5とOS補助を使うN01〜N04案を置き換える。

### 試験区分と振り分けの基本方針

**バックエンド試験・フロントエンド試験でカバーできないもののみ、アプリケーション結合試験に回す。** これは対象別の3区分であり、単体・結合などの試験水準や使用ツールとは区別する。

| 試験区分 | 確認する対象 | 使用手段 |
| --- | --- | --- |
| バックエンド試験 | 抽出・検索・索引・順位・周辺・編集・出力などの処理、公開API、CLI、接続を必要としないTauriコマンド内の処理/状態 | Rustの単体/API/性質/実CLI試験 |
| フロントエンド試験 | 入力操作、DOM・状態遷移、要求引数、応答の表示、保存値の扱い、画面構造・配色 | Playwright＋Tauri境界モック。既存Uケースと設計中のG01/G02 |
| アプリケーション結合試験 | 個別試験では観測できない配布資材の起動、実IPC・イベント配送、実セッション・永続化との接続 | Playwright＋実Tauri。下記の有効なEケースのみ |

設計時にはまず各不具合をバックエンド試験またはフロントエンド試験で再現できるか判定する。Tauriコマンド内の処理・セッション状態・直列化の規則も、実WebView2との接続なしで検証できるものはバックエンド試験で担当する。個別試験の不足はその区分で補う。個別試験が未実装であることや、実EXEで代表例を動かしたいことだけを結合試験へ追加する理由にしない。両者が成功しても残る接続上の不具合と、必要な最小の操作・観測を説明できる項目だけをEケースとして採用する。

| 確認すること | 個別試験の担当 | 結合試験でのみ残すこと |
| --- | --- | --- |
| 抽出、Unicode照合、あいまい距離、条件・一括の上限/全組合せ、順位 | 意味・計算はバックエンド試験。要求引数、強調、ラベル、表示順はフロントエンド試験 | E02の実検索要求/拒否/通知の往復、E06の別コマンドと一括通知の接続。形式やモードの全組合せは繰り返さない |
| 索引の鮮度、破損/旧版復旧、無書込、検索同値性、オプションの独立性 | 処理はバックエンド試験。チェックボックス・要求・削除後の画面はフロントエンド試験 | E04の削除コマンドから試験用DBへの到達 |
| Excel周辺・編集 | 抽出・範囲・リビジョン・文字コードはバックエンド試験。ID/tokenを渡す操作・拒否後の表示はフロントエンド試験 | E08/E09の実検索セッションからのtarget/draft解決、実保存と拒否の往復 |
| CSV/TSV/JSON/行列、BOM、引用、数式先頭対策、Report整合 | 変換はバックエンド試験。出力範囲・要求・状態・取消/拒否はフロントエンド試験U27〜U31 | 追加しない。ネイティブ保存経路は保証対象外 |
| 入力、絞り込み、折りたたみ、追加描画、フォーカス、画面構造・6テーマ | フロントエンド試験U/G | E11は実通知の複数バッチ配送と最終件数に限定。表示分岐や配色は繰り返さない |
| 設定復元・検索ライフサイクル | 保存値の処理・例外・状態遷移はフロントエンド試験。検索通知の生成・中断処理はバックエンド試験 | E07の実スレッド中断/終了後の受付、E10の実WebView2プロファイルの再起動復元とパス検証接続 |
| 生成器の再現性・在庫・アイコン素材、staging一覧/ハッシュ、EXE識別 | 共通の検証基盤としてRust生成器/xtask・静的確認で担当 | E01は配布資材の実起動に限定。ハッシュ計算や在庫確認を画面試験にしない |

旧E03の複数ルート/除外/パス規則、旧E05の条件範囲/順位は個別試験へ振り分け、独立した結合ケースを廃止する。実検索の接続と入力拒否の往復はE02で確認する。旧E12のTSV整形はバックエンド試験で担当する。`src-tauri`のformat_reportはRustのtable_text呼出しであり、固定Reportの変換確認を結合試験へ追加しない。廃止IDは再利用しない。

## 1. 現行と導入後の実行契約

| 入口 | 現行 | アプリケーション結合試験導入後の設計 |
| --- | --- | --- |
| `cargo xtask setup` | 固定lockfileでPlaywright/Chromiumを準備 | 継続。OS補助や別のGUIライブラリは導入しない |
| `cargo xtask ui` | フロントエンド試験54件（実HTML/CSS/JS＋境界モック） | 継続。G01/G02を同区分の拡張として追加 |
| `cargo xtask test` | バックエンド試験、生成器、フロントエンド試験 | 個別試験と検証基盤の全必須成功→Release EXEビルド→アプリケーション結合試験 |
| `cargo xtask build` | Windows Release EXEをビルド | 継続。ビルドのみの依頼では起動しない |
| `cargo xtask ci` | 既存一式→全必須成功時にReleaseビルド | testと同じ必須工程を実行し、試験済みEXEを成果物に採用。再ビルドしない |
| `cargo xtask exe` | 存在しない | 新設する診断入口。現在のソースからReleaseビルドし、有効なEケースを全件実行。G01/G02はuiで担当 |

この文書を追加しても現行コマンドの動作は変わらない。ランナー導入後は、自動テスト依頼に必要なビルド・実EXE起動・Playwrightによる操作を含め、別のGUI許可を求めない。対話的なAI操作・人による任意の目視確認は別依頼とする。実装・文書整備だけの依頼ではテスト・ビルド・起動へ進まない。

## 2. 接続・データ・判定

- 配布と同じRelease EXEに [Playwrightの `connectOverCDP`](https://playwright.dev/docs/webview2) で接続する。Release EXEで接続できるかはE01の導入時確認事項であり、今回確認した事実ではない。
- `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` のデバッグポートと `WEBVIEW2_USER_DATA_FOLDER` は起動する子プロセスだけに指定する。設定やデバッグ機能を製品コードへ常設しない。既存ポート・EXE・ブラウザーへ接続しない。
- 新しい試験用文書コピー、LOCALAPPDATA、WebView2プロファイルをケースごとに割り当てる。E10の再起動だけ同じ試験プロファイルを再利用する。親プロセス・利用者の環境や設定を書き換えない。
- 既存Rust生成器のcommon/context/office/issues、固定seed、ケース原本を使う。E11は試験用コピー領域に同じ検索語へ一致する205個のテキスト文書を用意し、固定相対パス一覧を期待値とする。期待値は仕様と固定ケースから採用し、今回のCLI出力を正解として採用しない。日本語・空白・絵文字を含む試験パスも用意する。
- 実EXEでは `window.__TAURI__`、invoke、イベント、検索結果をモックに置き換えない。イベント観測には実APIの追加購読を使い、画面の購読経路を変更しない。関数の内部状態や画面描画をテスト側で再実装しない。
- 結合試験の画面操作は、接続を確かめる最小限のDOM・状態、編集の実ファイル結果、索引削除の試験用DBで判定する。個別試験で判定済みの要求組合せ・描画・配色や、固定データを公開invokeへ直接渡す純粋な変換確認は追加しない。EXEのSHA256や環境版の収集はランナーの証跡処理とする。
- 1 worker、再試行なし。起動・接続は30秒、ケースは60秒を上限に、DOM・通知・プロセス状態を条件付きで待つ。固定sleepや再試行による合格化を行わない。
- Windows/WebView2/Node/Playwright、操作可能なWindowsセッションを前提とする。前提不足・CDP接続不可・ケース未実行は理由付きskippedとして記録し、全体は非ゼロとする。別ビルドやモックへ切り替えて成功扱いにしない。
- 終了時は試験が起動したPIDとその子プロセスだけを終了する。利用者の既存EXEや同名プロセスを一括終了しない。新規の試験データ・ログはoutputsに残し、履歴やキャッシュを自動再帰削除しない。

## 4. フロントエンド試験へ振り分ける構造・配色確認

G01（構造・キーボード）とG02（6テーマ・配色）は両方ともフロントエンド試験に所属させ、[フロントエンド試験設計](playwright-ui-test-plan.md#設計中のフロントエンド試験の拡張g01g02)で手順・期待結果を管理する。実EXEに同じ判定を追加しない。E01は資材の起動、E10は保存色1値の再起動復元だけを確認し、配色の網羅と区別する。スクリーンショット・画像比較・動画・トレースは [Playwright設定](https://playwright.dev/docs/test-use-options#recording-options)で無効を維持する。

## 5. OS連携の保証対象外

以下は自動試験の対象から除外する。手動確認を必須にせず、合格・skippedの件数に含めない。任意の実地確認を行った場合だけ、その環境と実測を別記する。

| 項目 | この試験体系では保証しないこと | 自動確認を残す範囲 |
| --- | --- | --- |
| ネイティブフォルダー選択（旧N01全項目） | 主/追加/除外欄の実Windowsダイアログでの選択・取消・Esc・特殊文字パス選択 | E02は検索ルート直接入力の実IPCを確認。複数欄/除外の要求引数・選択応答後の反映・取消・拒否はU03/U08 |
| ネイティブ保存（旧N02のダイアログ経由項目） | 実保存ダイアログ、初期ファイル名/フィルター、特殊文字保存先、取消/Esc、既存ファイル上書き、権限/共有ロックを含む実保存先への書込み | RustのCSV/TSV/JSON/行列生成・BOM・引用・式先頭対策。U27〜U31で対象件数・要求・操作可否・取消/拒否後の保持 |
| クリップボード（旧N03全項目） | 実Windowsクリップボードへの到達、他アプリ貼付、占有/競合、連続コピーの実OS状態 | U17/U28で渡す文字列・成功/失敗表示。TSV整形の正しさはRustのreport試験 |
| 既定アプリ起動（旧N04全項目） | Shell/関連付けを通じた対象文書の実起動・読込、同名/特殊文字パスの到達、削除や関連付け失敗時のOS経路 | U17で渡すパスと拒否表示。実EXEの検索・周辺・編集とは区別 |
| 排他ロック注入 | Rust補助によるファイル/クリップボード占有、Windows権限や共有競合の網羅 | 既存Rust試験で確認する失敗とUの境界拒否。E09は通常編集/外部変更で、排他ロックを扱わない |
| OS表示・Office互換性 | 実モニターのDPI、複数画面、Windows外枠、EXE/タスクバー/Alt+Tabのアイコン表示、実Officeでの見た目・計算・マクロ | フロントエンド試験G01/G02のDOM/配色測定、検証基盤のRustアイコン素材試験。素材一致をOS表示確認へ読み替えない |

Node.jsの標準機能による試験ファイルの作成・読取り・通常の編集バイト照合は使用する。ただし保存ダイアログを通っていない独立ファイル操作で、製品の保存経路を保証しない。OS連携が保証対象外でも、バックエンド試験・フロントエンド試験・アプリケーション結合試験と検証基盤の必須工程が成功すれば、その対象範囲の全体結果を成功としてよい。

## 6. 証跡・受け入れ・次の実装

各実行の `outputs/runs/<ID>/` に、既存工程のreportと独立した `exe/results.json`、工程ログ、失敗時のみ最大64,000文字のテキスト診断を残す。対象ソースcommit/dirty、ビルド版・EXEのSHA256/サイズ、WebView2/Playwright版、ケースID、期待値/実測値、タイムアウトや前提不足を記録する。別実行の成功ログを再利用しない。

受け入れ条件:

1. バックエンド試験・フロントエンド試験と検証基盤の既存必須工程を維持する。フロントエンド試験の拡張G01/G02、有効な結合試験E01/E02/E04/E06〜E11を全件実行する。廃止E03/E05/E12は実行・skipped件数に含めず、IDを再利用しない。選択診断の結果を全体合格に使わない。
2. 必須工程は失敗・skipped・flakyが0で、実EXEへの接続と実Rust処理の結果を確認できる。失敗後も独立したケースは実行し、全体終了コードへ反映する。
3. 保証対象外のOS項目は試験不足によるskippedとは区別する。除外を合格に数えず、将来拡張する場合も対象範囲を明示する。
