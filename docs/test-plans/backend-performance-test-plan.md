# バックエンド性能改善の確認方針

検索結果の意味を維持しながら、単語境界判定、語間の正規化、テキスト読込み、索引SQLの重複を削減する変更を確認する。機能基準は[Rust要求仕様](../specifications/rust-requirements.md)、実行範囲と入口は[開発手順](../development.md#テスト)、実装済み・設計のみの区別は[対象案件のIssue](https://github.com/kz-oshiro/docs-search/issues/19)を参照する。

## 変更と維持する契約

| 対象 | 変更 | 維持する契約 |
| --- | --- | --- |
| [照合](../../core/src/fuzzy.rs) | 原文の文字配列・正規化形・トークンを必要時に構築し、同じUnitの評価内で共有。ASCIIの変換をまとめる。位置表は一致候補がある形だけ構築し、連続する1バイト/1文字の対応をまとめる | 書記素ごとの変換、CRLF、Unicode文字位置、語句一致の優先度、通常/あいまいの分類・点数 |
| [一括](../../core/src/batch.rs)・[検索](../../core/src/lib.rs) | ファイル名・各Unitの前処理を256語まで共有。前処理の保持は1Unitの評価期間に限定する | 入力語順、最初の表記、1Unit/語につき1件、識別子境界、語別集計・中断 |
| [編集用リビジョン](../../core/src/lib.rs) | テキスト一致/条件根拠がある時だけ全文リビジョンを計算。初回は抽出した元バイトを再利用し、索引再利用時は一致したファイルだけ一度読み込む。元バイトはファイルの処理終了時に解放する | 全文・元行の変更検出、BOM/改行/文字コード、元一致範囲、32MiB上限。索引経由の読込み前後もサイズ・mtimeを検査する |
| [索引](../../core/src/index.rs) | SQL文の準備を接続内で共有。全Unitは1回のSELECT、絞った候補は最大500 IDごとに取得。tokensのunit_id索引を既存DBにも追加する | ID順、候補の和集合/積集合、NOTを含む全件評価、部分抽出を保存しない、更新中のロールバック・DB破損時の再抽出。候補IDの取得不足はエラーにする |
| [周辺取得](../../core/src/context.rs) | 鮮度確認で検証したシートメタデータを取得処理へ返し、同じJSONの再解析を省く | 破損メタデータ時の直接読込み、範囲・結合起点・保存書式、取得前後の変更検出 |

依存追加、公開API/CLI・invoke/event契約の変更、製品版・抽出仕様版の変更はない。SQLの追加索引は保存形式を変えず、既存のschemaVersion 2へ追加する。

## バックエンド試験

追加した回帰ケースは以下の5件。性能値の合否を時間依存の単体試験に組み込まず、期待する意味・範囲・件数を固定する。

| ID | 確認項目・手順 | 期待結果・実装先 |
| --- | --- | --- |
| BP01 | 16,384文字の連続aと末尾の独立したa、独立語のない連続aを通常/あいまいで評価する | 前者は末尾のexact=100、後者は先頭のsubstring=70。元範囲とstandard分類を保持。[fuzzy.rs](../../core/src/fuzzy.rs)のrepeated_substringsケース |
| BP02 | 同じ原文へßの展開、結合文字のcafé、区切りを除いた識別子、絵文字の一部分を順に照合し、CRLFを含む語句も評価する | 元のUnicode文字範囲・書記素範囲、方式・分類が固定期待値と一致。[fuzzy.rs](../../core/src/fuzzy.rs)のshared_viewsケース |
| BP03 | 絵文字付き1行へ256語と紛らわしい識別子を配置し、identifier/text・あいまいoff/onの4組で公開API検索する | 256件、入力順のtermId、各元範囲、語別の1ファイル/1箇所、編集アンカーを保持。[公開API](../../core/tests/requirements_v3.rs)のmany_batch_termsケース |
| BP04 | BOM/CRLF/絵文字のある検索結果から編集を取得し、別の行だけ同じバイト数で外部変更して再取得する | 初回の選択範囲はneedle。全文リビジョンで別行の変更も拒否し、元バイトを保持。[公開API](../../core/tests/requirements_v3.rs)のsearch_generated_revisionケース |
| BP05 | CLIで1,501行を直接・索引初回・再利用、通常/あいまいで検索し、0件・文書更新・削除まで確認する | 複数取得バッチでも全ヒットの順序・元範囲・全文リビジョンが直接検索と一致。再利用統計、更新後の1件、削除後の全索引表の0件を確認。[索引CLI](../../core/tests/cli_index.rs)のindexed_many_candidatesケース |

既存のUnicode・候補漏れ・直接/索引比較の[性質テスト](property-testing-test-plan.md)、[Office/順位/一括](office-ranking-batch-test-plan.md)、[条件](condition-search-test-plan.md)、[周辺](excel-context-test-plan.md)、[編集](issues-test-plan.md)も維持する。特にa_/a!、区切りだけの語、数字、Shift_JIS、NOT、抽出範囲の切替、壊れたsheets JSON、元バイトの変更、中断時の通知/終端集計を確認する。

自動テストの依頼を受けた次の担当は、この方針と対象案件の案件Issueを読んでルートで実行する。既存seedを残し、利用者のLOCALAPPDATAを試験に使わない。

```powershell
$env:PROPTEST_CASES = '1024'
$env:PROPTEST_RNG_SEED = '3000002'
cargo xtask test
```

設定前の環境値を保存し、終了後に戻す。現行入口はバックエンド試験・生成器/資材の検証と下記フロントエンド試験を実行し、`outputs/runs/<ID>/report.md` / `report.json` を原本にする。配布ビルドまで依頼された場合は[開発手順](../development.md#windows-ビルドと-ci)に従う。

## フロントエンド試験

新規ケースは追加しない。現行の必須ヘッドレスPlaywrightで通常/条件/一括の要求、結果の元範囲からの強調、順位・語別集計、中断・編集・周辺・出力を確認する。判定はDOM・状態・要求引数・テキスト記録で行い、画像・動画・トレースを使わない。画面・通知契約を変更していないため、ケースの意味と期待値は[既存設計](playwright-ui-test-plan.md)を維持する。

## アプリケーション結合試験

この変更の照合・リビジョン・SQL・メタデータはバックエンド試験で、要求/応答の画面処理はフロントエンド試験で観測できるため、新規の結合ケースは追加しない。[既存設計](playwright-exe-test-plan.md)の実コマンド/通知配送、結果IDから編集・周辺への往復は実EXEランナー導入後の範囲である。現行のtest/ci成功をその接続の検証へ読み替えない。

## 性能比較の手順・期待結果

性能計測とそのためのビルドも依頼された場合に実施する。自動試験の工程時間やxtaskの並列化だけで製品の検索速度を判定しない。

1. 変更前後を独立した比較用チェックアウトに用意し、同じRust・依存・Release設定でCLIをビルドする。基準コミットと差分、実行バイナリ、fixtureのハッシュを自動記録する。比較対象ごとに専用のLOCALAPPDATAを使う。
2. 同じ生成済み文書と固定語を使い、下表をそれぞれ5回以上実行する。初回は毎回新しい索引領域、再利用は同じ要求で事前作成した索引を使う。OSのファイルキャッシュとアプリの索引再利用を区別する。文書を変更するケースは別コピーを用意する。
3. CLIのstdoutをファイルへ保存し、開始から終了までの時間・プロセスCPU時間・PeakWorkingSet64・索引DBのサイズを計測スクリプトで収集する。終了コード、結果/順位/語別集計/Issue、発見/処理/抽出/再利用数も保存する。集計は中央値と範囲を自動算出する。タイムアウト時は成功値へ混ぜず、その入力と理由を残す。
4. 同じ結果・元範囲・順位・編集リビジョンを確認した上で時間と最大メモリを比較する。改善率の閾値は計測前に基準を採って決め、測定値を見てから成功基準を変えない。定量結果は実行の機械生成記録へ保存し、試験設計や実装状況へ転記しない。

| 負荷 | 手順 | 期待結果 |
| --- | --- | --- |
| 境界候補の多い長い行 | 連続aを4/8/16KiBとし、末尾の独立語あり/なしを通常/あいまいで比較する。大きな入力は短いものの測定後に増やす | 結果の優先度・範囲を維持し、候補ごとの全文配列化に起因する増大が抑えられる |
| 多数語 | 同じテキスト/Excelを1・32・256語、identifier/text・あいまいoff/onで、索引なし/初回/再利用に分けて比較する | 語数分の正規化形・位置表の再構築を減らし、語別結果・順位を維持する |
| テキスト読込み | 大きな複数ファイルで本文一致0件/少数/多数、ファイル名だけの一致を分ける | 初回の元ファイル二重読込みを除き、再利用の0件/ファイル名一致では編集用の全文読込みをしない。全文を読む一致ファイルは1回だけで、変更検出を維持する |
| 多数の索引Unit | 1,501件以上、短語/通常/条件/一括/あいまい、文書更新・削除を比較する。試験用DBでtokens削除のEXPLAIN QUERY PLANも保存する | 行ごとの読込みをまとめ、登録・削除のSQL準備を共有する。tokens(unit_id)のアクセス経路と結果の完全性を確認する |
| Unicode長行・不一致 | 日本語・結合文字・幅差・絵文字の長いUnitへ256語を照合し、一致0件/複数方式での多数一致を比較する | 位置表の遅延構築・保持期間を確認し、複数の正規化形を保持することによる最大メモリの悪化がないか調べる。速度だけで受け入れない |
| Excel周辺情報 | 多シート・保存書式の多いブックで索引再利用の5×5取得を繰り返し、壊れたメタデータも確認する | 同じJSONの二重解析を除き、値・書式・直接読込みへのフォールバックを維持する |
| 中断 | バックエンドAPIから同じ数の結果通知後に中断し、終端までの時間・保持結果を比較する | 既通知結果を保持し、同じsearchIdのcancelled終端が1回だけ届く。中断を通常完了に数えない |

速度・最大メモリ・中断応答の定量基準は未決定。試験コードの追加と確認方針の策定は、実行成功や性能向上の実測とは区別する。
