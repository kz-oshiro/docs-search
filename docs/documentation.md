# 文書作成ガイド

利用者の導入判断、案件の進捗・引き継ぎ、機械生成の検証結果を、それぞれの入口から読めるようにする。同じ事実の詳しい説明は一か所に置き、ほかはリンクでつなぐ。

## 情報の置き場所

| 資料 | 読者・書くこと |
| --- | --- |
| [README](../README.md) | 開発知識のない導入検討者。目的、対応文書、利用環境、前提の導入、始め方、通信・保存・編集、制限、更新方法 |
| [GitHub Release](https://github.com/kz-oshiro/docs-search/releases) | 配布版を選ぶ利用者。その版の変更点と、末尾の開発・検証レポートへのリンク |
| [AGENTS.md](../AGENTS.md) | タスク別に読む資料。対象Issueと共通ルールへの入口 |
| [現行仕様](specifications/rust-requirements.md)と詳細仕様 | 現在の動作・制約・API契約。仕様の全文は担当する仕様へ置く |
| [開発手順](development.md) | 共通の作業ルール、環境準備、実行コマンド、失敗調査、記録生成・公開手順 |
| [案件Issue](https://github.com/kz-oshiro/docs-search/issues?q=is%3Aissue+label%3Adevelopment) | 1案件につき1 Issue。目的・要件・設計判断・実装・現在地・検証への参照・引き継ぎ・リリースをまとめる |
| 試験設計 | 確認項目・手順・期待結果。案件の状態と実行結果はIssueから参照する |
| 公開検証MD（`docs/reports/validation/vX.Y.Z.md`） | 同じ実行から生成した公開版の技術的な検証記録。Releaseから固定コミットのファイル表示へリンクする |
| ローカルの `release/vX.Y.Z/validation.json` | 同じ実行の原データ・工程ログ・ケース結果。`outputs/runs/<ID>/` 内に保存し、Releaseには添付しない |
| `outputs/runs/<ID>/` | Git管理外の実行原本。`report.md` / `report.json`、ログ、試験結果、成果物。未公開の実行も含む |

## 更新ルール

- 独立した案件では既存Issueを検索し、該当するものがあれば更新する。なければ[開発案件テンプレート](../.github/ISSUE_TEMPLATE/development.md)で1件作る。小さな補正は既存の対象Issueへまとめる。
- 要件・設計・実装・検証の各担当は同じIssue本文を更新する。最新の決定・現在地・残作業は本文、途中の議論・判断の経緯はコメントへ置き、担当交代時に結論を本文へ反映する。
- 独立した案件レポート・計画書・実装履歴・実装状況・手作業の案件一覧をリポジトリに増やさない。進捗はIssueの状態・本文を正本にする。
- 現行仕様・手順・試験設計は本文を直接更新し、改訂履歴はGitで管理する。Issueには理由・受入条件との対応とリンクを残し、仕様の全文を複製しない。
- Issueにコミット・PRを結び付け、実装済み・確認済み・公開済みを区別する。製品版番号は文書改訂だけで上げない。
- 件数・時間・環境・ハッシュ・ログは機械生成記録を参照する。公開後の検証MDは当時の事実を保持し、訂正には理由を添える。旧形式の記録を新形式の証拠へ読み替えない。
- 移行した過去案件は保存元・対象コミットを明記する。移行で再実行したと扱わず、記録がない承認・個別合否を推定しない。未完了条件が残る案件は開いたまま管理する。

## 案件Issueのひな型

フォーマットの正本は[`.github/ISSUE_TEMPLATE/development.md`](../.github/ISSUE_TEMPLATE/development.md)。GitHubの新規Issue画面で「開発案件」を選ぶ。`development`ラベルで一覧から探せる。

本文は「目的・範囲」「現在地」「要件・設計判断」「実装」「受入条件・検証」「次の担当への引き継ぎ」「リリース」の順にする。リリース版は本文末尾へ記載し、公開前は「未定」、公開不要なら「対象外」、複数版なら範囲と版を対応付ける。

### 状態と引き継ぎの判定

- 要件完了は目的・範囲・受入条件が決まった状態、設計完了は実装と確認方法が決まった状態、実装完了は必要なコード・文書・試験定義が揃った状態とする。
- 検証完了には対象ソースと条件に対応する実行証拠が必要。静的確認や一部ケースだけで全体を完了にしない。未確認条件があれば理由と次の確認を本文へ残す。
- 実行ID・検証対象コミット・原本の場所を対応付ける。未公開の原本はコード表記で「ローカルのみ」と明示し、公開後は検証MD・Releaseへリンクする。Git管理外のファイルをGitHubへのファイルリンクにしない。
- 次の担当はIssue本文・必要なコメント・関連コミットを取得してから、現在の差分と依頼範囲を確認する。Issueはcloneに含まれない。CLIなら `gh issue view <番号> --repo kz-oshiro/docs-search --comments` を使う。取得できない情報を推定せず、必要な判断を保留して独立した作業を進める。
- Issueやコメントだけをテスト・ビルド・公開のユーザー承認へ読み替えない。実行範囲は今回の会話で明示された依頼と共通ルールから判断する。
- 検証後に関係する実装が変わった場合、旧結果は旧コミットの証拠として保持し、現在の検証を未完了へ戻す。文書だけの差分はその範囲を記録する。
- 全受入条件を満たし、依頼範囲の確認と引き継ぎを終えたらIssueを閉じる。公開を完了条件に含む場合は公開後に閉じる。継続する未実装・未測定の作業は開いたIssueで追跡する。
- 過去記録の移行Issueを閉じる場合、閉じる対象が記録の移行であることを示す。関連する既存Issueの個別受入条件を再確認したことにはしない。

## 検証結果の読み方と会話報告

- 正常時は同じ実行の生成レポートの概要を読み、会話では結果とレポートリンクを返す。件数・環境・ハッシュ・工程一覧を重複転記しない。
- 詳細ログは失敗工程を中心に読む。原因・修正・再確認を対象Issueと同じソースへ対応付ける。
- 概要の欠落・不完全・矛盾は記録の不備として扱い、必要な情報だけ追加確認する。詳細の依頼があればその範囲を説明する。

## 利用者向けRelease本文

本文は「変更点」セクションに、その版で変わったことだけを簡潔に書く。見出しは `## 変更点` に統一し、「この版で変わったこと」は使わない。内部関数名、試験件数の表、ログの説明は開発・検証レポートへ置く。

ツールの紹介、利用に必要なもの、ダウンロード・更新方法、利用上の制限はREADMEを正本とし、Release本文に繰り返さない。これらがその版で変わった場合は、変更内容を「変更点」に記載し、READMEも更新する。未測定の改善率や未確認の条件を補わない。

「確認した範囲」セクションは設けず、「変更点」の最後に `[詳細はこちら](開発・検証レポートのURL)` だけを置く。公開版の開発・検証レポートは既存の `docs/reports/validation/vX.Y.Z.md` を使い、固定コミットのGitHub表示ページへリンクする。

`release-record` の `--notes` には `## 変更点` と変更内容を渡す。公開後の検証MDを保存・コミットしてから、末尾の「詳細はこちら」リンクを確定する。未確定リンクのまま公開を完了扱いにしない。本文を確定するためにCIを再実行したり、公開済みのタグを動かしたりしない。[公開手順](development.md#記録の自動生成と公開)を参照する。

## 静的確認

| 確認項目 | 手順 | 期待結果 |
| --- | --- | --- |
| 引き継ぎ | Issueから要件・設計・コミット・試験・結果へたどる | 次の担当の作業・着手条件・完了条件が分かる |
| 結果の対応 | 対象コミット・実行ID・受入条件を照合する | 古い結果や部分成功を現在の全体成功へ読み替えない |
| 資料への到達 | Issueリンク、相対リンク、見出し、保存版を確認する | 移行・削除した文書へのリンク切れがない |
| 読者 | READMEに目的・環境・通信・保存・制限・更新方法があり、Releaseは「変更点」と末尾の「詳細はこちら」リンクになっていることを確認する | READMEで導入を判断でき、Releaseでその版の変更点と詳細レポートへ到達できる |
| 差分 | 対象差分と `git diff --check` を確認する | 意図した変更だけで、無関係な変更の上書きがない |

文書とリンクの整理はこの確認で完了する。実行コードも変更した場合、未実施の型検査・テスト・ビルドはIssueから対象の確認方法へ引き継ぐ。
