# 文書作成ガイド

読む人が現在の仕様・次の手順・実施結果を見分けられるよう、情報の置き場所を固定する。同じ事実の詳しい説明は一か所に置き、ほかはリンクで参照する。

## 情報の置き場所

| 文書 | 書くこと |
| --- | --- |
| [README](../README.md) | 製品概要、使い始め方、各資料への入口 |
| [AGENTS.md](../AGENTS.md) | タスク別に読む資料のリンク。機能別の資料は列挙しない |
| [現行仕様](specifications/rust-requirements.md)と詳細仕様 | 現在の動作・制約・API契約。全体、GUI、バックエンド、境界ごとの詳細へリンクする |
| [開発手順](development.md) | 共通の作業ルール、環境準備、実行コマンド、失敗の調べ方、結果記録・公開手順 |
| [試験設計](reports/implementation-status.md)から参照する対象文書 | 確認項目・手順・期待結果。分類は[試験区分と振り分け](test-plans/playwright-exe-test-plan.md#試験区分と振り分けの基本方針)、判定方法は[フロントエンド試験設計](test-plans/playwright-ui-test-plan.md)、OS連携の保証範囲は[結合試験設計](test-plans/playwright-exe-test-plan.md#5-os連携の保証対象外)に集約する |
| [実装状況](reports/implementation-status.md) | 実装済み・未実装と詳細へのリンク。試験の成功件数や実行ログを転記しない |
| 実装計画 | 未実装の変更内容と受け入れ条件。現在の仕様や完了報告を混ぜない |
| 実装報告 | 対象の変更と理由、静的確認、未実施の検証、引き継ぐ試験設計 |
| [実行・公開記録](releases/README.md) | 対象版/コミットと自動生成の実行・公開記録への入口。生成・公開方法は[開発手順](development.md#記録の自動生成と公開)を参照する |

## 更新ルール

- 既存の役割に収まる内容はその文書を更新する。新規文書は独立した読者・目的がある場合に限り、既存の入口からリンクする。
- 現行の仕様・開発手順・試験設計は同じファイルの本文を更新する。「方針更新」「今回未実施」などの追記で旧本文を読み替えさせず、改訂履歴はGitで管理する。製品版番号は付けず、文書改訂だけで製品版を上げない。
- 依存ツール・API契約・データ形式の版情報は必要な箇所に残す。実装報告・リリースノート・検証記録には対象版/コミットや報告時点を残し、後続の結果はリンクで案内する。過去の記録を現行仕様へ書き換えない。
- 試験設計は[バックエンド試験・フロントエンド試験・アプリケーション結合試験](test-plans/playwright-exe-test-plan.md#試験区分と振り分けの基本方針)の担当ごとに確認項目・手順・期待結果を書く。生成器・資材・ハッシュは共通の検証基盤として併記する。実装済み・設計のみ・検証済みを区別する。
- 手書きは変更点・理由・例外の判断と確認方針に絞る。結果の原本と参照・公開方法は[開発手順](development.md#記録の自動生成と公開)に従う。

## 検証結果の読み方と会話報告

- 正常時は、同じ実行の生成済みレポートの概要だけを読む。会話では依頼範囲の「結果＋レポートリンク」を返し、件数・環境・ハッシュ・工程一覧を重複転記しない。
- 詳細ログを読むのは失敗工程に絞る。失敗時の会話では原因・修正・再確認結果を必要な範囲で説明し、レポートへリンクする。
- 概要の欠落・不完全・矛盾は記録の不備として扱い、該当情報だけを追加確認する。ユーザーから詳細の依頼があれば、その範囲の説明を行う。

## 実装報告のひな型

報告の冒頭に対象変更と報告時点を書く。通常は会話の報告で足りる。次の担当が参照する確認方針は対象の試験設計に保存し、独立した実装報告が必要な場合だけ `docs/reports/` に作成する。

```text
対象: <変更名・基準コミット> / 報告時点: <日付>

1. 変更と理由
   <何を、なぜ変更したか。参照する仕様へのリンク>
2. 静的確認
   <実施した内容と結果。実行検証と区別する>
3. 未実施の検証
   <依頼範囲で実施していない工程>
4. 次の担当の確認方針
   <対象の試験設計へのリンク。確認項目・手順・期待結果>
```

## 静的確認

| 確認項目 | 手順 | 期待結果 |
| --- | --- | --- |
| 指示の移動 | 変更前の各指示と参照先の本文を照合する | 実行範囲・確認条件・報告方法が欠けず、同じ説明の重複がない |
| 資料への到達 | タスク別の入口から相対リンクと見出しを確認する | 共通ルールと対象の仕様・試験設計へ到達できる |
| 文書の役割 | 現行文書、設計のみの項目、過去の記録を読み分ける | 現在の手順に過去の未実施報告が混ざらず、履歴や結果を現在の保証へ読み替えない |
| 差分 | 対象文書の差分と `git diff --check` を確認する | 意図した文書変更だけで、空白エラーや無関係な変更の上書きがない |

文書とリンクの整理だけなら、この確認で完了する。動作に影響する変更の検証は対象の試験設計と依頼範囲に従い、バックエンド・フロントエンド・アプリケーション結合の各試験を実施する。
