# 文書作成ガイド

利用者の導入判断、開発担当の引き継ぎ、機械生成の検証結果を、それぞれの入口から読めるようにする。同じ事実の詳しい説明は一か所に置き、ほかはリンクでつなぐ。

## 情報の置き場所

| 文書 | 読者・書くこと |
| --- | --- |
| [README](../README.md) | 開発知識のない導入検討者。目的、対応文書、利用環境、前提の導入、始め方、通信・保存・編集、制限、更新方法 |
| [GitHub Release](https://github.com/kz-oshiro/docs-search/releases) | 配布版を選ぶ利用者。その版の変更点、利用条件、ダウンロード・更新、既知の制限、検証記録へのリンク |
| [AGENTS.md](../AGENTS.md) | タスク別に読む資料。開発レポートと共通ルールへの入口 |
| [現行仕様](specifications/rust-requirements.md)と詳細仕様 | 現在の動作・制約・API契約。仕様の全文は担当する仕様へ置く |
| [開発手順](development.md) | 共通の作業ルール、環境準備、実行コマンド、失敗調査、記録生成・公開手順 |
| 開発レポート（`docs/reports/development/`） | 案件ごとに要件・設計・実装・検証・公開と次の作業をつなぐ。各担当が同じMDを更新する |
| [開発レポート一覧](reports/development/README.md) | 案件名・状態とレポートへのリンクだけを置く。詳しい計画・履歴・残作業は各レポートへ集約する |
| 試験設計 | 確認項目・手順・期待結果。案件の状態と実行結果は開発レポートから参照する |
| 公開検証MD（`docs/reports/validation/vX.Y.Z.md`） | 同じ実行から生成した公開版の技術的な検証記録。Releaseから固定コミットのファイル表示へリンクする |
| ローカルの `release/vX.Y.Z/validation.json` | 同じ実行の原データ・工程ログ・ケース結果。`outputs/runs/<ID>/` 内に保存し、Releaseには添付しない |
| `outputs/runs/<ID>/` | Git管理外の実行原本。`report.md` / `report.json`、ログ、試験結果、成果物。未公開の実行も含む |

## 更新ルール

- 独立した開発案件を始めるとき、開発レポートを1枚作る。要件決め・設計・実装・検証を別のモデルが担当しても、工程別の報告は増やさず同じファイルを更新する。小さな補正は対象案件のレポートを更新する。独立した計画書・実装履歴・実装状況は増やさず、計画と現在地も案件のレポートに記載する。
- 現行仕様・手順・試験設計は本文を直接更新し、改訂履歴はGitで管理する。過去の「未実施」を現在の指示へ混ぜない。製品の版番号は文書改訂だけで上げない。
- 詳細仕様と試験手順は担当文書へ置く。開発レポートには判断の要点・差分・対応関係を残し、全文を複製しない。
- 各担当は工程終了時に状態・成果物・未決事項・次の作業を更新する。既存の実装済み・確認済み・公開済みを、コードや証拠なしに変更しない。
- 手書きは目的、変更理由、設計判断、受入条件との対応、未完了事項に絞る。件数・時間・環境・ハッシュ・ログは機械生成記録を参照する。
- 公開後の検証MDは当時の事実を保持する。訂正には理由を添え、再実行した結果と混同しない。旧形式の記録を新形式の証拠へ読み替えない。

## 開発レポートのひな型

保存先は `docs/reports/development/YYYY-MM-DD-<案件名>.md`。日付と案件名を識別子とし、担当やモデルが変わっても名前を変えない。[開発レポート一覧](reports/development/README.md)から未着手・進行中・完了したすべての案件へリンクする。

```markdown
# <案件名> 開発レポート

案件ID: <ファイル名の日付・案件名> / 更新日: <日付>
基準コミット: <SHA> / 実装対象: <SHAまたは未コミットの作業ツリー>

## 目的・範囲
<利用者の問題、実現する変化、対象外>

## 現在地
| 工程 | 状態 | 根拠・残作業 |
| --- | --- | --- |
| 要件 | 未着手／進行中／完了／保留／対象外／記録なし | 決定内容・参照先 |
| 設計 | 同上 | 採用方針・未決事項 |
| 実装 | 同上 | コミット・差分・未コミットの範囲 |
| 検証 | 同上 | 対象コミット・実行ID・レポート。未実施理由 |
| 公開 | 同上 | タグ・Release。不要なら対象外 |

## 要件・設計判断
<採用した判断と理由、未決事項。詳細仕様・関連案件へのリンク>

## 実装
<実装した範囲、設計からの変更理由、差分への参照、残作業>

## 受入条件・検証
| 条件ID | 条件・仕様参照 | 実装参照 | 試験設計・ケース | 結果への参照／未確認理由 |
| --- | --- | --- | --- | --- |
| <既存要求IDまたは案件内AC-01> | <要点と仕様の節> | <差分・対象> | <確認方法> | <実行ID・レポートの節、未実施・失敗・対象外> |

## 次の担当への引き継ぎ
- 最初に読む資料: <仕様・設計・共通ルール>
- 着手条件: <対象コミット、現在の差分、依頼された実行範囲>
- 次の作業: <未完了の具体的な作業>
- 確認方法・完了条件: <コマンドや静的確認、期待結果、必要な参照>

## リリース

対象リリース: <vX.Y.Zへのリンク／未定／対象外。複数版の場合は対応する範囲>
```

### 状態と引き継ぎの判定

- 要件完了は目的・範囲・受入条件が決まった状態、設計完了は実装と確認方法が決まった状態、実装完了は必要なコード・文書・試験定義が揃った状態とする。
- 検証完了には対象ソースと条件に対応する実行証拠が必要。静的確認や一部ケースの成功だけで全体を完了にしない。未確認の受入条件があれば、その工程と理由を残す。
- 検証結果は実行ID・検証対象コミット・原本の場所を対応付ける。未公開の原本パスはコード表記で「ローカルのみ」と明示し、公開後は検証MD・Releaseへのリンクを追加する。
- 次の担当は記録されたコミットと現在の差分を確認してから着手する。検証後に関係する実装が変わった場合、旧結果は旧コミットの証拠として残し、現在の検証を未完了へ戻して再確認事項を書く。文書だけの差分はその範囲を記録する。
- 前の担当の未決事項を推測で確定しない。過去資料の移行では、確認できない承認日時・実装コミット・個別ケース対応を「記録なし」とし、後続の全体検証を個別条件の成功へ読み替えない。
- リリース版は各レポートの末尾「リリース」へ記載する。公開前は「未定」、公開が不要なら「対象外」、複数版なら対象範囲と版を対応付ける。公開後の文書改訂を新しい配布版へ読み替えない。
- 通常の共通ルールを案件ごとに複製しない。対象案件固有の確認範囲・例外と、次の担当が行える作業を残す。

## 検証結果の読み方と会話報告

- 正常時は同じ実行の生成レポートの概要を読み、会話では結果とレポートリンクを返す。件数・環境・ハッシュ・工程一覧を重複転記しない。
- 詳細ログは失敗工程を中心に読む。原因・修正・再確認を開発レポートと同じ対象へ対応付ける。
- 概要の欠落・不完全・矛盾は記録の不備として扱い、必要な情報だけ追加確認する。詳細の依頼があればその範囲を説明する。

## 利用者向けRelease本文

開発知識のない利用者が、その版を導入するか判断できる文章にする。「何が変わるか」「必要なもの」「ダウンロード・更新」「既知の制限」を書き、詳しい検証はリンクで案内する。内部関数名、試験件数の表、ログの説明を本文の中心にしない。

利用条件は版の実装と配布物から確認する。未測定の改善率、未確認のOS・端末、未設定のライセンス条件を補わない。通信は検索機能、WebView2の導入・更新、共有先や起動したアプリを区別する。

`release-record` の `--notes` には利用者向けの本文を渡す。公開後の検証MDを保存・コミットしてから、本文にその固定コミットのGitHub表示リンクを入れる。未確定リンクのまま公開を完了扱いにしない。本文を確定するためにCIを再実行したり、公開済みのタグを動かしたりしない。[公開手順](development.md#記録の自動生成と公開)を参照する。

## 静的確認

| 確認項目 | 手順 | 期待結果 |
| --- | --- | --- |
| 引き継ぎ | レポートから要件・設計・差分・試験・結果へたどる | 次の担当の作業・着手条件・完了条件が分かる |
| 結果の対応 | 対象コミット・実行ID・受入条件を照合する | 古い結果や部分成功を現在の全体成功へ読み替えない |
| 資料への到達 | 入口、相対リンク、見出し、保存版を確認する | 移行・削除した文書へのリンク切れがない |
| 読者 | READMEとReleaseの目的・環境・通信・保存・制限を確認する | 開発手順を読まずに導入を判断できる |
| 差分 | 対象差分と `git diff --check` を確認する | 意図した変更だけで、無関係な変更の上書きがない |

文書とリンクの整理はこの確認で完了する。実行コードも変更した場合、未実施の型検査・テスト・ビルドは開発レポートから対象の確認方法へ引き継ぐ。
