# docs-search の回帰試験設計

入力は不具合、要求変更、対象差分。仕様を根拠に再現条件と確認項目・手順・期待結果を作り、依頼された試験コードやデータへ反映する。

最初に [AGENTS.md](../../../AGENTS.md) と [共通ルール](../../../docs/development.md#エージェントの作業ルール)を読む。実行範囲は今回の依頼から判断する。

## 試験を配置する

1. [現行仕様](../../../docs/specifications/rust-requirements.md)と [開発レポート一覧](../../../docs/reports/development/README.md)から対象の要求・試験設計を読む。設計のみの項目と現在のランナーを区別する。
2. [試験区分と振り分け](../../../docs/test-plans/playwright-exe-test-plan.md#試験区分と振り分けの基本方針)に従い、不具合を観測できる区分を選ぶ。処理・状態はバックエンド、入力・DOM・要求と応答表示はフロントエンド、両者で観測できない実接続だけをアプリケーション結合試験へ回す。個別試験が不足していれば、その区分を補う。
3. [試験コードとデータの対応](../../../tests/README.md)から既存のケース原本・生成器・試験コードを選ぶ。似た試験を拡張し、同じ条件を別区分でも繰り返す場合は検出する不具合の違いを説明する。

## バックエンドの再現条件を作る

- 文書の再現には [独立した生成器](../../../test-support/src/lib.rs)と [テンプレート](../../../test-support/templates/README.md)を使う。共通ケースは [ケース原本](../../../tests/fixtures/backend-cases.json)、専用ケースは対象のCLI/API試験と照合する。期待値は仕様と固定入力から決め、今回の検索結果をそのまま正解にしない。
- データを変える場合はケース契約、生成器、在庫確認、対象の試験設計を対応させる。既存の移行比較への影響がある場合だけ、その比較方針も更新する。生成する必要がある場合は開発手順の入口と保存先の条件に従う。
- 索引や候補抽出の変更では、同じ入力・オプションの直接検索、初回索引、再利用索引を比較する。最終評価で一致する単位を候補から落とさない性質と、結果の同値性を確認する。
- 組合せを生成して調べる場合は [性質テストの設計](../../../docs/test-plans/property-testing-test-plan.md)と [既存の性質](../../../core/src/property_tests.rs)を読む。独立した期待モデルを用意し、一致する入力や境界値も生成する。
- proptestの失敗では縮小例を調べ、[保存seed](../../../core/proptest-regressions/property_tests.txt)を保持し、意味が分かる固定回帰も追加する。戦略変更でseedの再現内容が変わる可能性を考慮する。期待値の変更は仕様上の根拠がある場合に限る。

## フロントエンド・接続の再現条件を作る

画面の変更時は [フロントエンド試験設計](../../../docs/test-plans/playwright-ui-test-plan.md)と対象の [既存spec](../../../tests/ui/specs)を読む。

- 実HTML/CSS/JavaScriptの初期化と操作を使い、[モック](../../../tests/ui/support/tauri-mock.mjs)はTauri境界の要求・購読・応答に限定する。検索や順位計算をモックへ再実装しない。
- 要求の引数、searchId/sequence、DOMと状態遷移を観測する。関連する拒否・取消・遅延・古い応答を再現し、固定sleepに頼らず観測対象の状態を待つ。
- 判定と診断はテキストで行い、画像・動画・トレースの扱いは試験設計に従う。モックへの固定応答の表示を、実コアの計算や実IPC配送の証拠にしない。
- 接続だけに残る不具合では [アプリケーション結合試験設計](../../../docs/test-plans/playwright-exe-test-plan.md)を読む。実EXEランナーの導入状態を確認してから手順を選び、設計の存在を実行可能・検証済みと扱わない。

## 確認方針を残す

対象の試験設計に、要求、不具合の再現入力、担当区分、手順、期待結果を反映する。実装・静的確認・実行結果を区別し、報告は [文書作成ガイド](../../../docs/documentation.md#開発レポートのひな型)に従う。
