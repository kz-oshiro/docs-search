# docs-search の文書整備

入力は変更内容と対象資料。現在の動作、次の手順、実施した結果を読者が区別できるよう、既存文書の本文と参照を更新する。

## 更新する文書を選ぶ

1. [AGENTS.md](../../../AGENTS.md)、[共通ルール](../../../docs/development.md#エージェントの作業ルール)、[文書作成ガイド](../../../docs/documentation.md)を読む。
2. 依頼対象のコード・差分・計画・実行記録から事実を確認する。[現行仕様](../../../docs/specifications/rust-requirements.md)、[実装状況](../../../docs/reports/implementation-status.md)、過去の記録が示す時点を見分ける。記憶や過去の報告だけで現在の実装・検証済み状態を決めない。
3. 文書作成ガイドの「情報の置き場所」に従い、各事実の正本を選ぶ。現在の仕様、未実装の計画、確認手順、実行結果をそれぞれの既存文書へ置き、詳しい説明を一か所に保つ。

## 本文と参照を更新する

- 現行文書は本文を直接更新し、旧本文を読み替えさせる追記を積み重ねない。過去の実装報告や検証記録は当時の事実を保ち、後続結果を参照で案内する。
- 新しい文書は独立した読者・目的がある場合だけ作り、既存の入口から到達できるようにする。AGENTS.mdはタスク別の資料への入口として維持する。
- 実装済み・設計のみ・確認済み・公開済みの記述をコードや証跡と照合する。試験設計の存在を検証結果として扱わず、古い実行時点の「未実施」を現在の手順へ混ぜない。
- 試験設計では [試験区分と振り分け](../../../docs/test-plans/playwright-exe-test-plan.md#試験区分と振り分けの基本方針)に沿って、対象の確認項目・手順・期待結果を更新する。保証範囲の詳しい説明は担当する試験設計へ参照させる。
- テスト・ビルド・公開の件数、環境、ハッシュ、ログは [記録生成と公開](../../../docs/development.md#記録の自動生成と公開)に従い、原本や生成記録を参照する。手書きは変更点・理由・例外の判断・確認方針に絞る。
- 文書改訂だけで製品版を上げない。契約やデータ形式の版は必要な箇所へ残し、現在の手順へ過去の製品版・ツール版を固定しない。

## 静的確認と報告

[文書の静的確認](../../../docs/documentation.md#静的確認)に従い、更新した資料と関連する入口を確認する。

- 相対リンクを記載ファイルのディレクトリから解決し、ファイルと見出しに到達できることを確認する。移動・削除したパスを参照する箇所を検索し、現行パスか意図した履歴参照へ直す。
- 同じ判断に関する本文と参照が食い違わず、実行範囲・確認条件・報告方法を保っていることを確認する。構造変更では依頼対象に関連する参照を重点的に調べる。
- 対象差分と空白エラーを確認し、既存の無関係な変更を保つ。文書とリンクの整理はこの静的確認で完了する。

変更した正本・理由・静的確認の結果を簡潔に報告する。製品の実装変更も含む場合は [実装報告のひな型](../../../docs/documentation.md#実装報告のひな型)を使い、実行範囲に応じた検証と次の担当の確認方針を区別する。
