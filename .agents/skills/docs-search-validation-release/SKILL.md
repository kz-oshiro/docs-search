# docs-search の検証・公開

依頼された範囲をCargoの入口で実行し、対象ソースと同じ実行の証跡を使って結果・成果物・公開状態を確認する。

## 実行する範囲を決める

1. [AGENTS.md](../../../AGENTS.md) と [共通ルール](../../../docs/development.md#エージェントの作業ルール)を読み、今回の依頼がテスト・ビルド・公開のどこまで含むか把握する。既に明示された依頼を有効な承認として扱い、同じ確認を繰り返さない。
2. 直近の実装報告、[実装状況](../../../docs/reports/implementation-status.md)、対象の試験設計から確認項目・手順・期待結果を読む。
3. [テスト手順](../../../docs/development.md#テスト)、[ビルドとCI](../../../docs/development.md#windows-ビルドと-ci)、[記録生成と公開](../../../docs/development.md#記録の自動生成と公開)のうち依頼に対応する箇所を読む。対象ソース、既存差分、前提、[現在の入口](../../../xtask/src/main.rs)を確認する。

ツールの版、件数、seed、必須工程、追加ランナーと記録生成の導入状態は参照先で確認する。文書内の将来のコマンドや過去の成功記録を、現在の実行契約へ読み替えない。

## 実行と失敗調査

- 共通入口の `cargo xtask` を使う。準備・個別診断・全件検証・配布ビルドを依頼範囲に合わせて選び、選択したケースだけの成功を全体合格の証拠にしない。
- 実行中は検証対象のコードを変更しない。修正が必要なら該当実行を不成功の証跡として残し、修正後の対象で必要な工程を再実行する。
- ランナーが保存する記録の読む範囲と会話報告は [文書作成ガイド](../../../docs/documentation.md#検証結果の読み方と会話報告)に従う。概要が示す失敗工程のログとテキスト診断を調べる。
- 必須工程の欠落・skipped・flaky・結果取得失敗を成功にしない。独立した残りの工程を続行する方針を維持し、終了コードと同じ実行の記録を照合する。
- 証跡を実行IDで揃える。異なる実行の成功ログや別ビルドのEXEを混ぜず、重なる工程の時間を総所要時間として加算しない。

## 公開対象を照合する

公開が依頼範囲に含まれる場合、最新の [記録生成と公開](../../../docs/development.md#記録の自動生成と公開)に従って準備から公開後の照合まで進める。

1. 成功したCIの対象コミット・開始終了時の差分・必須工程と、公開するソースの関係を確認する。試験後の変更が再検証を必要とするかは開発手順の条件で判定する。
2. 同じ実行に保存されたEXE、サイズ、SHA256、対象タグを照合する。最新mainとタグが異なる場合は差分を確認し、実際の公開対象をタグのコミットで特定する。
3. 記録生成が導入済みなら、その入口でRelease本文と検証記録を生成する。利用者向けの変更点・理由・例外だけを短く手書きし、件数・環境・正常ログを文書へ重複転記しない。未導入なら導入後の形式へ旧記録を読み替えず、現行手順と実際の証跡で対応する。
4. 依頼されたpush・タグ・Release作成・添付を完了し、公開後にリモートのタグ、Release状態、アセットのサイズ・digestを同じ保存EXEと照合する。不一致や取得失敗は理由を報告し、公開照合済みと扱わない。

## 結果を報告する

[試験区分と振り分け](../../../docs/test-plans/playwright-exe-test-plan.md#試験区分と振り分けの基本方針)に沿って生成済みの概要を確認し、未実装・未実施を実際の成否から区別する。正常時の会話は結果とレポートへのリンクに絞り、失敗時の説明は文書作成ガイドに従う。

EXEのビルドをアプリケーション結合試験の成功に数えない。保証範囲とGUI操作の条件は現行の試験設計・共通ルールを参照し、過去の必須手動確認票や一律の「GUI未検証」を追加しない。記録への入口は [公開・検証記録](../../../docs/releases/README.md)と開発手順を使う。
